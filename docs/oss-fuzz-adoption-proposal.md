# 面向 OSS-Fuzz 的自动构建修复系统：价值主张、试点与沟通方案

最后更新：2026-10-14  
适用代码分支：`fix-fuzzing-build`

## 1. 本文目的

本文用于向 OSS-Fuzz 维护者介绍当前系统，并指导如何以可验证、低风险的方式推动试点和
后续集成。目标不是宣称“LLM 已能自动合并补丁”，而是把系统定位为一个受约束的构建故障
处置产品：它发现故障、保留上下文、生成最小修复候选、执行验证、给出可审计证据，并将
最终合并权保留给项目维护者。

本文将能力分为三类：

- **已实现**：已存在于当前分支并有代码或实验产物证据；
- **可直接利用现有产物实现**：需要增加展示/规则代码，但已有所需输入；
- **提议路线**：尚未实现，不能在对外沟通中表述为现有能力。

## 2. 一句话定位

> 一个面向 OSS-Fuzz 构建失败的、可审计的修复候选生成与验证流水线：从真实失败日志出发，
> 提取可复现的修复输入，生成并验证最小补丁候选，再把证据、差异和人工决策边界一并交给
> OSS-Fuzz 与上游项目维护者。

更保守的表述是：**系统自动化的是诊断、候选补丁、验证和材料准备，不自动替代维护者的
合并决策。**

## 3. 可以向 OSS-Fuzz 推销的价值

### 3.1 从“失败告警”升级到“可处理工作项”【已实现】

当前系统可以从 OSS-Fuzz 状态与真实构建日志开始，完成：

```text
当前失败项目
  -> 下载状态边界上的成功/失败日志
  -> 提取版本、仓库、引擎、sanitizer、架构、基础镜像等元数据
  -> 生成面向修复代理的单项目 benchmark YAML
  -> 自动修复与构建验证
  -> 保存补丁、日志、轨迹和结果报告
```

对 OSS-Fuzz 的直接价值是减少人工将一个“红色构建状态”转换为“可交给项目维护者处理的完整
问题包”的时间。维护者不必先手工寻找失败日志、对应源码版本、OSS-Fuzz 提交和构建环境。

### 3.2 风险受控的候选修复，而非黑盒改写【已实现】

系统保留每个修复项目的输入元数据、构建日志、修复运行日志、修复轨迹、验证结果、变更
文件和 patch。现有报告代码还生成失败链、补丁证据页和英文修复摘要。

对外可强调：

- 修改必须经过 fuzz-build 验证，成功状态不是纯模型文字判断；
- 补丁和验证证据可单独审阅；
- 缺失或格式错误的可选轨迹不会让报告空白，而是显示证据不可用；
- 失败项目、未完整元数据项目和跳过原因都会保留，而不是被静默丢弃。

### 3.3 与 OSS-Fuzz 的现有运维节奏相容【已实现】

前置流程使用 OSS-Fuzz 当前状态和公开构建日志，并以 OSS-Fuzz 项目名为单位处理。日志选择
保留关键状态边界，而非盲目下载所有历史日志；All 模式还能保留最后成功与当前失败的对照。

这让系统适合先作为“失败项目分诊与补丁候选服务”接入，而不要求修改 OSS-Fuzz 的构建器、
ClusterFuzz 或项目维护流程。

### 3.4 可渐进部署，默认不扩大风险【已实现】

三阶段可独立执行：仅抓取日志、仅从既有日志提取、仅对静态 YAML 修复，或组合运行。前置
流程通过显式参数开启，未启用时原有 oss-fuzz-gen 实验行为不变。

建议向 OSS-Fuzz 提出分阶段试点，而不是要求一次性接管全部失败项目：

1. 只生成报告与候选，不创建上游 PR；
2. 只向少量同意参与的项目提交人工审核 PR；
3. 根据接受率、回归率、维护者反馈决定是否扩大范围。

### 3.5 429/配额故障不是被掩盖，而是被控制和记录【已实现，但需真实批量复验】

系统曾遇到 Vertex 429，因此修复代理现已加入进程内单飞、6 秒请求间隔、429 专用指数退避
与共享冷却、以及内部修复轮失败路由。对外应诚实说明：代码和单元测试已提交，但仍需要以
真实批量实验量化 429 发生率、重试次数、成本和修复成功率。

这比无控制并发地触发模型调用更接近一个可运营系统。

## 4. 维护者真正可能关心的问题，以及建议回答

| OSS-Fuzz/项目维护者问题 | 建议回答 |
|---|---|
| 为什么不用人工直接修？ | 人工仍决定是否合并；系统减少失败分诊、环境对齐、候选编写和验证材料整理的重复工作。 |
| LLM 会不会产生危险补丁？ | 系统只生成候选；补丁必须有构建验证、完整 diff 和证据。默认不自动合并。 |
| 会不会修改大量无关代码？ | 当前补丁优化指令明确要求以验证后的基线和故障责任区域为边界，避免临时/生成文件；仍需要维护者审查。 |
| 失败或模型不可用怎么办？ | 记录失败、跳过原因和运行证据；429 有节流、退避与内部轮处理。不会将模型错误伪装为修复成功。 |
| 如何知道修复对应哪个历史环境？ | benchmark 记录 OSS-Fuzz SHA、上游 SHA、基础镜像摘要、日志 URL、引擎、sanitizer 和架构。 |
| 需要把整个系统部署到生产吗？ | 不需要。建议先作为离线/PR 实验试点，以少量项目输出候选 PR 包；通过指标后再讨论常态化。 |
| 这会增加 OSS-Fuzz 基础设施风险吗？ | 当前实现是 oss-fuzz-gen PR 实验中的可选用户态工作流，不要求替换 OSS-Fuzz 核心构建路径。 |

## 5. 可信度分级：应如何设计和对外表达

### 5.1 原则

不要使用“近乎 100% 可信、可直接 merged”这样的绝对承诺。构建通过只证明该固定环境下的
构建验证通过，不能替代上游 API 兼容性、安全性、维护性和项目治理判断。

建议用**处置等级**而非“模型置信度”表述。等级由可检查的证据规则产生，不能仅由模型自评。

### 5.2 建议等级【提议路线；尚未实现为自动规则】

| 等级 | 建议名称 | 证据门槛 | 允许动作 |
|---|---|---|---|
| A | 高证据候选 | 原始失败和候选均有保存；补丁后构建验证通过；变更小且限定在明确责任文件；无人工后编辑；无模型/工具异常。 | 自动生成 PR 草稿，维护者快速审阅；仍不自动合并。 |
| B | 可审阅候选 | 构建验证通过，但变更跨多个文件、包含依赖/构建逻辑调整，或根因证据不充分。 | 生成 PR 草稿，要求项目维护者完整代码审阅。 |
| C | 需要深入审查 | 有候选但验证不完整、复现不一致、涉及安全敏感/大范围改动，或出现模型/工具异常。 | 不自动向上游发 PR；仅保留报告和人工任务。 |
| D | 未修复/不可用 | 构建仍失败、元数据不完整、日志/环境不可得、429 重试耗尽等。 | 不发 PR；记录失败原因，等待人工或后续重试。 |

高证据候选也应使用“**可自动创建草稿 PR**”而非“自动合并”。如果 OSS-Fuzz 或上游项目未来
明确授权某个极窄范围的自动合并规则，应另行记录项目级政策、回滚路径和监控指标。

### 5.3 现有系统离该功能的距离

现有产物已经可提供大部分输入：状态、构建验证、patch、变更文件、修复轨迹、日志和最终
摘要。需要新增的部分是：

1. 将证据整理为可机器判定的等级规则；
2. 将等级、触发条件和阻塞原因显示到 HTML 报告；
3. 记录人工审阅结论和人工修改；
4. 实现仅对 A/B 创建草稿 PR 的显式授权流程；
5. 统计各等级的接受率、回退率和维护者反馈，校准规则。

## 6. 透明度：从自动候选到人工提交的完整链路

维护者关注的不只是最终 commit，还包括“自动系统做了什么、人工又改了什么”。建议把每个
PR 的信息组织为三层。

### 6.1 自动阶段【已有大部分证据】

- 失败日志和解析出的根因线索；
- 固定环境元数据（SHA、镜像摘要、引擎、sanitizer、架构）；
- 自动候选 patch 和变更文件；
- 验证命令/结果、修复轮数、失败链和代理日志。

### 6.2 人工阶段【需要新增记录机制】

- 人工在自动候选之上的 diff；
- 每一处人工修改的原因；
- 是否重新运行了 OSS-Fuzz 构建验证；
- 人工确认的风险与未解决问题。

推荐实现方式是保存三个明确版本，而不是覆盖自动结果：

```text
candidate.patch          # 自动代理通过验证后的原始候选
human-review.patch       # 人工相对 candidate.patch 的后续修改
final.patch              # 最终拟提交内容
```

报告应同时显示这些差异。这样“人工最小化”不会掩盖自动代理原始结果。

### 6.3 对外 PR/邮件模板【可由现有产物生成，需模板化实现】

```markdown
Subject: [OSS-Fuzz build fix] <project>: <简短故障描述>

Hi <maintainer>,

OSS-Fuzz detected a build failure for <project> on <error_date>. We prepared
a candidate fix using an evidence-backed repair workflow.

Failure:
- OSS-Fuzz log: <fuzzing_build_error_log>
- Environment: OSS-Fuzz <oss-fuzz_sha>, upstream <software_sha>,
  <engine>/<sanitizer>/<architecture>
- Observed cause: <concise root-cause summary>

Proposed change:
- <one-to-three bullets explaining the patch>
- Patch: <link or attached diff>

Validation performed:
- <exact fuzz-build command or validation result>
- Result: <passed / limitations>

Automation disclosure:
- Candidate generated by the OSS-Fuzz build-repair workflow.
- <No human changes / Human follow-up changes are attached and documented.>
- Confidence tier: <A/B/C>; this remains a maintainer-reviewed proposal.

Please let us know whether this change matches the intended build and release
policy for the project. We are happy to revise or close the proposal.
```

向 OSS-Fuzz 维护团队沟通时，附上一个包含失败日志、原始/最终 patch、验证结果和报告链接的
小型证据包，比仅提供“模型修复成功”更有说服力。

## 7. 推荐的联系与试点方式

### 7.1 先问需求，而不是先要求合并代码

建议先向 OSS-Fuzz 维护者提出简短问题：

1. 当前构建失败分诊中最耗时的环节是什么：发现、复现、定位、补丁准备，还是与上游沟通？
2. 他们能接受的自动化边界是什么：仅报告、草稿 PR，还是特定项目的受控 PR？
3. 哪些类型的项目或修复绝不能自动提 PR？
4. 维护者希望看到哪些验证证据、补丁大小限制和披露内容？
5. 是否有 3–5 个明确失败、愿意参与试点的项目？

这些问题既表达合作意图，也能防止把系统设计成维护者不需要的功能。

### 7.2 最小试点建议

建议的第一轮试点：

- 选择 3–5 个近期、持续失败且维护者愿意参与的项目；
- 只运行“发现 → 候选 → 验证 → 报告”，不自动创建上游 PR；
- 将每个项目结果标为 A/B/C/D，并请维护者评价根因准确度、补丁可维护性和报告可读性；
- 第二轮才对维护者明确同意的 A/B 候选创建草稿 PR；
- 定期报告接受率、拒绝原因、平均人工节省时间、429/运行成本和回归情况。

### 7.3 给 OSS-Fuzz 维护者的初始说明（可直接改写发送）

```markdown
We have integrated an opt-in OSS-Fuzz build-repair workflow into an
oss-fuzz-gen PR experiment. It starts from real OSS-Fuzz build logs, records
the corresponding source and OSS-Fuzz revisions, produces a candidate patch,
and validates it with the fuzz-build workflow. It preserves the log, patch,
validation result, and repair trace for review.

We are not proposing automatic merges. We would like to run a small,
maintainer-reviewed pilot that first produces evidence packages only. Based on
your feedback, the next step could be draft PRs for a narrowly selected set
of high-evidence candidates.

Could you advise which part of the current build-failure workflow is most
costly, what evidence you would require for a candidate patch, and whether
there are a few suitable projects for a small pilot?
```

## 8. 不应过度推销的内容

以下说法在当前阶段不应使用：

- “可以安全自动合并所有修复”；
- “已证明 LLM 修复没有回归”；
- “429 已在所有批量规模下完全解决”；
- “所有失败项目都可自动复现/修复”；
- “当前 HTML 报告已展示人工修改前后 diff”（尚未实现）；
- “系统已经可自动向上游创建 PR/发送邮件”（尚未实现）。

正确说法是：系统已经在 oss-fuzz-gen PR 实验中完成了前置链路和修复接入；它能够生成有
证据的修复候选，下一步是通过小规模、维护者参与的试点来证明质量和确定接入方式。

## 9. 推进 OSS-Fuzz 集成前的验收清单

- [ ] 至少完成一个“抓取 → 提取 → 修复 → 报告”的真实小规模端到端实验；
- [ ] 记录每个项目的构建验证、修复状态、429 重试与运行成本；
- [ ] 与 OSS-Fuzz 确认试点项目和可接受的自动化边界；
- [ ] 实现/验证可信度等级规则，并在报告中展示其证据；
- [ ] 实现候选 patch、人工修改和最终 patch 的可追溯展示；
- [ ] 形成可审阅的草稿 PR/邮件模板，但保持人工触发和人工合并；
- [ ] 根据维护者反馈调整筛选、验证和披露要求；
- [ ] 再讨论将功能从 oss-fuzz-gen PR 实验提升为 OSS-Fuzz 的常态化流程。

## 10. 面向 OSS-Fuzz 的推荐讲述逻辑

本节可用于首次会议、邮件说明或演示开场。讲述顺序应是“维护负担 → 已验证能力 → 风险
边界 → 小规模试点 → 共同建设”，不要从模型能力或“自动合并”开始。

### 10.1 建议的核心表述

> OSS-Fuzz 已经能够及时发现构建失败，但把失败状态变成一个可交给上游维护者审阅的修复
> 工作项，通常仍需要人工收集日志、确认版本和环境、定位问题、准备补丁并反复验证。我们
> 在 oss-fuzz-gen PR 实验中集成了一条可选流水线，目标是自动化这些重复的准备和验证工作，
> 而不是替代维护者的设计判断或合并权。
>
> 系统从真实 OSS-Fuzz 失败日志出发，记录对应的 OSS-Fuzz SHA、上游 SHA、基础镜像、
> fuzzing 引擎、sanitizer 和架构；随后生成候选补丁并执行 fuzz-build 验证。每一个候选
> 都保留失败日志、环境元数据、diff、修复轨迹和验证结果，因此维护者看到的不是一句“模型
> 认为已修复”，而是一份可审计的修复证据包。
>
> 我们不建议自动合并。第一步希望与 OSS-Fuzz 选择少量当前失败项目做试点：先只生成候选
> 和报告，由维护者评价根因、补丁质量和验证证据；只有在维护者明确同意的范围内，第二步
> 才考虑生成草稿 PR。这样可以把自动化收益带入现有流程，同时保持代码所有权和风险决策仍
> 在 OSS-Fuzz 与项目维护者手中。

### 10.2 讲述时按优先级强调的现有优势

1. **端到端、基于真实失败的处置能力**：不是脱离生产环境的补丁生成器，而是从真实失败
   日志开始，完成日志获取、元数据提取、候选修复与构建验证。
2. **可审计而非黑盒**：保留失败日志、OSS-Fuzz SHA、上游 SHA、基础镜像、补丁、修复
   轨迹、验证结果和报告，支持维护者独立复核。
3. **维护者始终掌握合并权**：默认不自动合并；系统交付的是候选与证据，适合作为分诊和
   修复辅助工具。
4. **可渐进试点**：日志抓取、元数据提取、可选复现和修复可独立或组合运行；可以从少量
   项目开始，而非一次性改变 OSS-Fuzz 的核心构建流程。
5. **减少无效计算与噪声**：Key/All 模式、状态边界筛选和黑名单机制减少无意义历史日志、
   已停止项目和重复处理。
6. **具备可运营性考虑**：已加入 Vertex 429 节流、退避、共享冷却和内部轮恢复；应表述为
   “已实现并有测试”，并承诺在试点中公开其真实效果。
7. **已有实验与报告接入点**：系统已在 oss-fuzz-gen PR 实验中运行，能利用现有修复报告、
   patch 和证据展示机制。
8. **已具备草稿 PR 所需的核心信息**：项目、失败、版本环境、候选 patch 和验证结果均可
   归档；尚未自动创建上游 PR，因此可先由人工控制发送时机。

### 10.3 主动说明的“下一步共同建设”

在介绍完现有能力后，应主动把下列内容作为希望与 OSS-Fuzz 一起定义的路线，而不是隐藏
其尚未完成状态：

1. **标准化 PR/邮件材料**：自动生成故障、改动、验证、自动化参与程度和人工修改说明。
2. **前置流程报告摘要**：在 HTML 报告中直观展示日志筛选、黑名单、元数据接纳/拒绝原因。
3. **真实运营指标**：持续统计修复成功率、上游接受率、人工修改率、回归率、耗时、成本和
   429 重试率，以数据而非演示说服长期集成。
4. **证据驱动的可信度分级**：把候选划分为高证据、可审阅、需深入审查和未修复，并展示每
   个等级的客观依据。高证据的含义是“可创建草稿 PR”，不是“可自动合并”。
5. **自动与人工修改的完整追溯**：同时保存自动候选 patch、人工增量 patch 和最终 patch，
   使最小化或人工修订不会掩盖原始自动结果。
6. **项目级安全策略**：对依赖升级、基础镜像修改、大范围 diff、安全敏感项目和特定语言
   设置更严格的审批条件或禁止自动提 PR。

### 10.4 希望 OSS-Fuzz 回答的收口问题

讲述最后应把讨论转向需求确认：

> 如果先进行一个不自动发 PR 的小规模试点，OSS-Fuzz 最希望减少的是哪一步人工工作？对于
> 一个候选修复，您认为必须展示哪些验证证据？哪些项目或修改类型应被排除在试点之外？
> 是否可以共同选择 3–5 个项目，用维护者反馈和接受率来决定下一阶段的自动化边界？

这一收口可以避免“推销一个既定方案”，并把后续集成转化为与 OSS-Fuzz 共同定义的受控
试点。
